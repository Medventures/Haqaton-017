# Подпись согласия пациента через SIGEX

Актуальность исследования: 30.09.2026. Это технический контракт интеграции. Успешное подписание настоящим сертификатом пациента ещё требует отдельной проверки с владельцем сертификата; синтетическая проверка ниже этого не заменяет.

## Что подписывается

Пациент подписывает сохранённый PDF согласия, который ему показан перед действием. В PDF должны входить версия текста, идентификатор согласия, идентификатор пациента, ИИН и время формирования. Документ формируется один раз: повторное построение PDF после подписи может изменить его байты. Сервер сохраняет исходный PDF, SHA-256 и CMS, связывая результат с этой конкретной попыткой.

Подпись случайного кода при входе врача через `/api/auth` не является подписью согласия пациента. Подтверждение согласия не должно выдаваться на основании успешного входа врача.

## Серверный контракт SIGEX

Официальный [API документов](https://sigex.kz/support/developers/api-documents/) описывает следующую последовательность:

| Запрос | Данные | Успешный ответ |
| --- | --- | --- |
| `POST /api` | JSON: `signType:"cms"`, `signature:<base64 DER CMS>`, `title`, `description`, `settings` | `documentId`, целочисленный `signId`, `data` — извлечённые вложенные данные в base64 |
| `POST /api/{id}/data` | Исходный PDF; `Content-Type: application/octet-stream`, правильный `Content-Length` | `documentId`, `signedDataSize`, `digests`, `dataArchived`, `tempStorage` |
| `POST /api/{id}/verify` | Тот же исходный PDF и заголовки | `documentId`, `dataArchived`, `tempStorage` |

Настройки регистрации:

```json
{
  "private": true,
  "signaturesLimit": 1,
  "strictSignersRequirements": true,
  "signersRequirements": [{"iin": "IIN000000000000", "ca": "nca"}],
  "publicDuringPreregistration": false,
  "publicWhileLessThanSignatures": 0,
  "forceArchive": false,
  "tempStorageAfterRegistration": 0
}
```

Нули — синтетическая заглушка: сервер подставляет ИИН выбранного пациента. `strictSignersRequirements` распространяет требование на первую подпись. Регистрация проверяет CMS и собирает OCSP/TSP; завершение регистрации требует `/data`. SIGEX не принимает подпись без положительного OCSP. `/verify` проверяет подписи на момент регистрации, используя сохранённые OCSP/TSP. Поля `valid:true` в ответе нет. [Источник](https://sigex.kz/support/developers/api-documents/).

Собственные проверки приложения:

1. Брать PDF и ожидаемый ИИН из серверной записи, а не из заверений браузера.
2. Принимать только одну attached CMS. Строго декодировать `data` из ответа регистрации и сравнивать с исходным PDF целиком; дополнительно хранить SHA-256 для контроля архива.
3. Проверять форму каждого ответа, отсутствие `message`/`requestID`, совпадение `documentId`, размер документа и ожидаемые типы полей. HTTP 200 сам по себе успеха не означает.
4. Не активировать согласие до завершения всей последовательности. При ошибке, отказе, таймауте или истечении попытки оставлять его неподписанным.
5. Не записывать CMS, PDF, ИИН и служебные URL QR в журналы. Технический результат хранить отдельно от пользовательского сообщения об ошибке.

## Закрытый доступ и сведения сертификата

`private:true` ограничивает чтение метаданных. Для `GET /api/{id}` нужна сессия соответствующего подписанта SIGEX либо разрешённая информационная система организации. Режим входа `external:true` не создаёт cookie сессии SIGEX. Для автоматизированной работы предусмотрен mTLS на `https://sigex.kz:10443`: клиентский сертификат добавляется в настройки организации и необходимые списки доступа. [Аутентификация и контроль доступа](https://sigex.kz/support/developers/auth-and-access-control/).

При разрешённом чтении метаданных конкретную подпись выбирают по `signId`. Доступны `userId`, `subjectStructure`, `serialNumber`, `from`, `until`, `storedAt`, `ocsp.certStatus`, `ocsp.producedAt`, `ocsp.thisUpdate`, `tsp.timeStamp`. Временные значения заданы в миллисекундах. [Структуры ответа](https://sigex.kz/support/developers/api-documents/).

Доступность `/data` и `/verify` для **существующего закрытого документа без сессии** не удалось подтвердить синтетическим вызовом. При отказе доступа приложение должно сообщать о невозможности завершить проверку и не активировать согласие. Нельзя обходить ограничение переключением `private:false`. Также нельзя подставлять вымышленные ФИО, сроки сертификата или время TSP: если метаданные не получены, они остаются неизвестными. ИИН может быть подтверждён требованием регистрации, но это не означает получения всего сертификата.

`forceArchive:false` не гарантирует отсутствия архивирования на стороне SIGEX: оно может быть включено настройками подписанта. Сохранение PDF в собственном архиве приложения не следует подменять обещанием, что документ нигде больше не обрабатывается.

## NCALayer

Передаётся base64 сохранённого PDF в метод `sign` модуля `kz.gov.pki.knca.basics`. Для attached CMS:

```js
{
  format: 'cms',
  data: pdfBase64,
  signingParams: { decode: true, encapsulate: true, digested: false, tsaProfile: {} },
  signerParams: { extKeyUsageOids: ['1.3.6.1.5.5.7.3.4', '1.2.398.3.3.4.1.1'] },
  locale: 'ru'
}
```

Это параметры подписи физическим лицом. Закрытый ключ остаётся в средстве подписи пациента. Выбор сертификата на клиенте не заменяет серверное ограничение ИИН. [Официальный клиент SIGEX, `basicsCMSParamsAttached` и `basicsSignerSignPerson`](https://github.com/sigex-kz/ncalayer-js-client/blob/master/ncalayer-client.js).

## eGov QR и eGov mobile

1. `POST /api/egovQr` с `description` и необязательным `whenDone.backUrl` возвращает `expireAt`, `qrCode`, ссылки запуска и `dataURL`/`signURL`.
2. На полученный `dataURL` отправляется JSON:

```json
{
  "signMethod": "CMS_WITH_DATA",
  "documentsToSign": [{
    "id": 1,
    "nameRu": "Согласие пациента Smart Consult",
    "nameKz": "Smart Consult пациентінің келісімі",
    "nameEn": "Smart Consult patient consent",
    "document": {"file": {"mime": "@file/pdf", "data": "BASE64_FROZEN_PDF"}}
  }]
}
```

3. `GET` полученного `signURL` возвращает `documentsToSign[0].document.file.data` с CMS. Ответ проходит ту же серверную проверку документа.

Оба запроса могут ждать действий приложения на телефоне; их выполняет фоновая задача с ограниченным сроком. Ссылки берутся из ответа, не конструируются вручную. `expireAt` задан в миллисекундах. При `status:"CANCELED"` сервис возвращает исходные неподписанные данные: такой ответ необходимо отклонить. Проверяются также метод, количество документов и ожидаемый `id`. [Официальный базовый API eGov](https://sigex.kz/support/developers/api-egov-basic/).

## Настройки приложения и границы готовности

Используются существующие `SIGEX_ENABLED` и `SIGEX_URL=https://sigex.kz`. Отдельный API key для описанного публичного API не предусмотрен. mTLS-клиент и чтение закрытых метаданных требуют отдельной настройки организации; существующий `SIGEX_URL` сам по себе не добавляет клиентский сертификат.

Реализованный контракт проверяющего модуля: `consent_sigex.verify_document_signature(pdf_bytes, cms_base64, expected_iin)`. При успехе он возвращает `verified`, `signer_iin`, `provider`, `provider_document_id`, целочисленный `provider_signature_id`, `document_sha256`, `certificate_verification:"registration_time"`, `strict_signer_requirements:true`; при неуспехе — `ConsentVerificationError`. `verified` возвращается только после регистрации, сопоставления вложенных байтов и успешного завершения `/data` и `/verify`.

Переключатель `CONSENT_SIGNATURE_REQUIRED` реализован в конфигурации; значение по умолчанию и в шаблоне — `true`. При `true` ручная отметка не разрешает голосовую запись и AI-обработку: сервер проверяет действующую подписанную запись согласия, включая ИИН, а worker повторяет проверку при обработке задания. Режим `false` оставлен для совместимости и изолированных тестов; на рабочем сервере он не используется. Переключатель не меняет строгость проверки самой подписи: ручная отметка не отображается как электронная подпись.

## Выполненная синтетическая проверка

30.09.2026 выполнены вызовы с проверкой TLS, без сертификатов пациентов и без персональных данных. SIGEX сообщил версию `v1.16.1`.

| Вызов | Фактический результат |
| --- | --- |
| `GET /api/version` | HTTP 200, версия сервиса |
| `POST /api`: закрытая регистрация со строгим ИИН и строкой, заведомо не являющейся CMS | HTTP 200, `message:"Failed to parse signature"` и `requestID` |
| `POST /api/{случайный отсутствующий id}/verify`: синтетические байты | HTTP 200, `message:"Document not found"` и `requestID` |

Эти проверки подтверждают доступность маршрутов и обработку ошибок, но **не** успешную криптографическую проверку, отклонение действующей подписи другого ИИН или доступ к существующему закрытому документу. Последние сценарии требуют контролируемого подписания владельцем действующего сертификата. Общая форма ошибок описана во [введении к SIGEX API](https://sigex.kz/support/developers/intro/).

Независимая проверка helper с подменённым HTTP-транспортом прошла 9 сценариев: принятие полного успешного ответа с целочисленным `signId`; отклонение ошибки регистрации с HTTP 200, строкового и логического `signId`, другого вложенного PDF, несовпадающего идентификатора `/data`, ошибки доступа `/verify`, другого идентификатора `/verify` и неполного ответа проверки. Эти проверки подтверждают поведение кода; настоящая проверка криптографии остаётся на стороне SIGEX.


## XML входа и восстановление подписания (30.09.2026)

Вход, регистрация и привязка ИИН теперь подписывают читаемый одноразовый XML
`authentication`: сервис, назначение, origin, серверный nonce, срок действия и
пояснение, что это не согласие пациента. NCALayer получает `format:xml`, eGov —
`signMethod:XML` и `documentXml`, согласно
[базовому API eGov](https://sigex.kz/support/developers/api-egov-basic/).

Сервер сравнивает все поля с выданным challenge, запрещает DTD/ENTITY, внешние
ссылки, вложенные/множественные подписи и неподдерживаемые трансформации. SIGEX
получает единственный `ds:Signature` и канонизированные подписанные байты.
ИИН из сертификата становится доверенным только после строгой проверки SIGEX.
Срок XML-входа остаётся пять минут; успешную попытку можно использовать один раз
только в выдавшем её браузере. Для старых уже начатых CMS-попыток сохранён старый
проверяющий контракт.

Согласие остаётся неизменяемым PDF с CMS. Полученная вовремя подпись сохраняется
зашифрованной до внешней проверки. На проверку выделено до 15 минут; это не
продлевает срок сканирования QR. При временном сбое проверка повторяется без
новой подписи. После регистрации сохраняется контрольная точка, чтобы повторный
запрос не регистрировал документ заново. Long-poll повторяется при транспортном
обрыве до получения HTTP-ответа, как допускает документация SIGEX.

Опрос статуса восстанавливает незавершённую задачу. Интерфейс возобновляет опрос
после возврата из eGov, фокуса окна и перезагрузки. Методы QR, NCALayer и ссылка
запуска eGov Mobile доступны при входе, привязке ИИН и подписании согласия.
Статус «Подпись получена — проверяем сертификат» не предоставляет согласие и не
равен «Подписано». Ошибки содержат этап проверки, без персональных данных и CMS.

Текущий запуск API использует один процесс; защита от одновременного long-poll
действует внутри него. Для масштабирования API на несколько процессов нужна
межпроцессная аренда задач.

Ранее неудачная серверная попытка сохранила только общую ошибку SIGEX; точный
этап установить по ней невозможно, исходная подпись не сохранилась. Исправления
восстановления проверены синтетическими тестами, а не действующей ЭЦП пациента.
Для окончательной проверки конкретного случая владелец должен начать новую
попытку и подписать её в eGov/NCALayer. Нельзя проставлять успех вручную либо
делать документ публичным для обхода проверки.
