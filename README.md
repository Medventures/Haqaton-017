## Проблема

Врач тратит часть приёма на ручное заполнение листа консультации: жалоб, анамнеза, результатов осмотра и назначений. Перенос разговора в структурированную запись требует времени и проверки. При использовании облачных моделей дополнительно необходимо контролировать передачу персональных и медицинских данных.

## Решение

Smart Consult помогает подготовить черновик листа по разговору врача и пациента. Врач проверяет распознанные сведения, исправляет поля и утверждает результат.

1. Врач входит по паролю либо ЭЦП, находит пациента по ФИО/ИИН или создаёт карточку.
2. Оформляет согласие на запись и обработку данных с ЭЦП пациента через NCALayer, QR или ссылку eGov Mobile.
3. Начинает первичный или повторный приём, записывает разговор либо загружает аудиофайл. До проверки ЭЦП согласия доступно ручное заполнение.
4. Распознавание выделяет реплики, таймкоды и голоса. LLM определяет роли участников и дополняет поля, сохраняя ранее внесённые сведения.
5. Врач сохраняет черновик или проверяет и утверждает лист. Проверенный результат доступен по API МИС; PDF открывается отдельно.

Запись передаётся фрагментами по 20–30 секунд; предварительные реплики появляются во время разговора, черновик дополняется примерно раз в минуту. После «Закончить диалог приёма» обрабатывается остаток и выполняется итоговый анализ. [Подробнее о потоковой обработке](docs/live-recording.md).

ИИ отдельно предлагает дополнительные анализы, обследования и предварительные варианты диагноза. Эти подсказки **не являются диагнозом или назначением**, не включаются в итоговый PDF и не передаются в МИС. Окончательное решение и ответственность остаются за врачом.

### Подписание на компьютере и телефоне

| Устройство | Доступный способ |
| --- | --- |
| Компьютер | NCALayer с ЭЦП на ПК или QR, который сканируется телефоном |
| Телефон / планшет | Ссылка для открытия eGov Mobile на этом же устройстве |

Способы выбираются по устройству, а не по ширине окна браузера. Для NCALayer нужно запустить локальное приложение и разрешить соединение с ним. Клиент сначала подключается к `wss://localhost:13579/`, при недоступности соединения пробует `wss://127.0.0.1:13579/`.

Вход и привязка ИИН подписывают одноразовый XML; согласие пациента — точные байты PDF с CMS-подписью. Возврат из eGov Mobile сам по себе не означает успеха: интерфейс ждёт локальную серверную проверку ЭЦП НУЦ, показывает её состояние и позволяет повторно запросить статус. [Подробности и границы проверки](docs/sigex-patient-consent.md).

### Защита конфиденциальности

- **До записи.** Приложение напоминает не произносить ФИО, ИИН, телефон, точный адрес и другие сведения, по которым можно узнать человека. В разговоре используйте обозначения «пациент», «врач», «родственник» и только необходимые для консультации сведения. Напоминание не заменяет согласие пациента.
- **Согласие.** Запись и AI-обработка доступны только после проверенной ЭЦП пациента (`CONSENT_SIGNATURE_REQUIRED=true`, включено по умолчанию). Обычной отметки врача недостаточно; до подписания доступно ручное заполнение. Сервер локально проверяет подпись, ИИН подписанта, точные байты документа, цепочку НУЦ и отзыв через OCSP; отзыв согласия блокирует новую обработку, сохраняя архив.
- **Перед LLM.** Сервер маскирует известные данные карточки и найденные по шаблонам ИИН, телефоны, email, даты, имена и адреса. Маскирование применяется также к клиническим полям и ручным изменениям, передаваемым при повторной генерации. В кабинете можно проверить и исправить обезличенный текст, заглушить выбранные реплики в копии аудио.
- **При облачном ASR.** В режиме OpenAI исходное аудио, включая фрагменты записи, отправляется провайдеру **до распознавания и маскирования**. В нём могут остаться персональные и медицинские данные. При согласии на этот режим автоматический анализ OpenAI может запускаться без отдельного ручного подтверждения маскирования. Для распознавания без передачи исходного аудио внешнему AI-провайдеру используйте собственный ASR.
- **На собственных моделях.** ASR и LLM могут работать на том же компьютере или доверенном сервере в закрытой сети/VPN. Тогда AI-запросы идут только на эти настроенные узлы. ЭЦП/SIGEX и интеграция с МИС — отдельные внешние подключения; выбор локальных моделей сам по себе не делает весь сервис офлайн.
- **Хранение и доступ.** Карточки, медицинские тексты и аудиозаписи шифруются на уровне приложения; для поиска используются HMAC-индексы. Пароли защищены Argon2, сессии — HttpOnly-cookie. Служебные идентификаторы, связи, времена и статусы не зашифрованы. Сайт работает по HTTPS; секреты хранятся только на сервере, не передаются во Vue и не коммитятся.
- **Разграничение доступа.** Пациентов могут искать все авторизованные врачи. Черновики, расшифровки и аудио доступны врачу приёма; проверенные листы других врачей видны в истории пациента. МИС получает утверждённые приёмы в пределах ключа врача. Действия фиксируются в журнале аудита.

**Автоматическое маскирование не гарантирует полной анонимности:** косвенные признаки, редкие обстоятельства и ошибки распознавания могут позволить узнать человека. Медицинская информация остаётся конфиденциальной даже без ФИО. Архив хранится без автоматического удаления; сроки хранения и доступ необходимо определить для конкретного внедрения. `ENCRYPTION_KEY` и `INDEX_KEY` нужно сохранять в защищённой резервной копии отдельно от БД.

### Интеграция с МИС

Ключ выпускается в «Настройки → Интеграция с МИС» и передаётся как `Authorization: Bearer <ключ>`. Он показывается один раз; повторный выпуск отзывает предыдущий.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/v1/integration/encounters` | Список утверждённых приёмов; фильтры `since`, `patient_id`, пагинация `offset`/`limit` |
| `GET /api/v1/integration/encounters/{id}` | Данные пациента, клинические поля, расшифровка и роли |
| `GET /api/v1/integration/encounters/{id}/recordings` | Архив записей приёма |
| `GET /api/v1/integration/encounters/{id}/recordings/{recording_id}/audio` | Исходное аудио в пределах доступа ключа |
| `POST /api/v1/encounters/{id}/send-to-mis` | Исходящая отправка проверенного листа из сессии врача; тело `{ "version": N }` |

Интеграция МИС предназначена для передачи медицинских данных и **не является обезличенным AI-запросом**. В неё не включаются отдельные ИИ-подсказки. После правок лист требует повторной проверки врачом. Пример исходящего клиента: [examples/mis_client.py](examples/mis_client.py); демонстрационный приёмник вымышленной МИС: [examples/mock_mis.py](examples/mock_mis.py). Для отправки из кабинета задаются `MIS_URL` и `MIS_TOKEN`; используется `Idempotency-Key` с идентификатором и версией приёма.

## Архитектура

| Компонент | Назначение |
| --- | --- |
| `ui` — Vue 3 / Nginx | Кабинет врача и запросы к `/api`; локальный адрес `http://localhost:5173` |
| `api` — FastAPI | Авторизация, пациенты, приёмы, ЭЦП, PDF и API МИС; локальный порт `8010` |
| `worker` — Python | Фоновые задания распознавания, маскирования и заполнения клинических полей |
| `db` — PostgreSQL 17 | Отдельная база `medhub`; Compose хранит её в томе `postgres_data` |
| `migrate` — Alembic | Одноразовый запуск миграций перед API и worker |
| ASR / LLM | Независимо настраиваемые облачные API или собственные сервисы |

API и worker используют общий том `audio_data` для зашифрованных записей. В стандартном Compose порты UI и API привязаны к `127.0.0.1`, PostgreSQL не публикует порт на хост. Для установки на существующий сервер нужна отдельная БД `medhub`; существующую базу `postgres` изменять не следует.

## Запуск

### Требования и установка

Для проверки ЭЦП нужен комплект библиотек SDK НУЦ в `backend/verifier/lib/`, который не включён в Git: [инструкция подготовки](backend/verifier/README.md). Подготовьте его до сборки Docker; для backend вне Docker также нужны Java 17+ и скомпилированный модуль проверки.

Для запуска приложения нужен Docker Engine с Compose v2 либо Docker Desktop с Linux containers. Приведённый скрипт настройки выполняется в PowerShell. Для разработки интерфейса отдельно нужны Node.js 22 и pnpm 11.25.0; для backend вне Docker — Python 3.12, PostgreSQL и ffmpeg.

```powershell
git clone --branch main https://github.com/Medventures/Haqaton-017.git
cd Haqaton-017
./scripts/setup.ps1
# Выберите настройки ASR и LLM ниже и заполните .env.
docker compose up --build -d
```

`setup.ps1` создаёт `.env` из [.env.example](.env.example), генерирует ключи шифрования, пароль PostgreSQL и код приглашения. Существующий `.env` не перезаписывается. Для регистрации используйте `REGISTRATION_CODE` из своего окружения.

После запуска: [интерфейс](http://localhost:5173), [Swagger](http://localhost:5173/api/docs), [API health](http://localhost:8010/api/health).

### Два пути настройки моделей

**Распознавание речи (ASR) и языковая модель (LLM) настраиваются независимо.** Можно использовать обе модели локально, обе через облачный API или смешанный вариант: например, собственный ASR и облачную LLM.

| Компонент | Собственные / локальные модели | Внешний API |
| --- | --- | --- |
| ASR — речь и голоса | faster-whisper + pyannote; непосредственно в worker или отдельный доверенный ASR-сервис | OpenAI `gpt-4o-transcribe-diarize` |
| LLM — поля и роли | Ollama, например `qwen3:8b`, на том же ПК или своём сервере | OpenAI либо провайдер с OpenAI-совместимым API |

#### Путь 1: через API

В `.env` установите значения ниже и **самостоятельно заполните** пустой `OPENAI_API_KEY` серверным ключом проекта:

```dotenv
ASR_PROVIDER=openai
OPENAI_API_KEY=
LLM_PROVIDER=openai
LLM_MODEL=gpt-5.6-terra
LLM_IS_CLOUD=true
INSTALL_LOCAL_AI=false
```

Один ключ используется обоими OpenAI-адаптерами. Распознавание использует модель с диаризацией; LLM работает через Responses API со строгой JSON-схемой, `reasoning.effort=low` и `store=false`. Этот параметр не означает гарантированного отсутствия хранения со стороны провайдера. [Проверка выбора LLM](docs/llm-selection.md).

Для другого облачного LLM-провайдера замените только LLM-настройки:

```dotenv
LLM_PROVIDER=openai_compatible
LLM_URL=https://provider.example/v1
LLM_MODEL=your-json-capable-model
LLM_API_KEY=
LLM_IS_CLOUD=true
```

`provider.example` и имя модели — заглушки; укажите адрес, модель и ключ своего провайдера. Совместимость конкретного сервиса нужно проверить. Универсального адаптера ко всем облачным ASR нет: основной готовый облачный путь — OpenAI.

#### Путь 2: собственные модели на этом или другом ПК

Для ASR на доверенном сервере и LLM в Ollama:

```dotenv
ASR_PROVIDER=self_hosted
ASR_URL=http://host.docker.internal:8090
ASR_API_KEY=
INSTALL_LOCAL_AI=false
LLM_PROVIDER=ollama
LLM_URL=http://host.docker.internal:11434
LLM_MODEL=qwen3:8b
LLM_IS_CLOUD=false
```

`host.docker.internal` обозначает компьютер, на котором работает Docker Desktop. Если модели находятся на другом ПК, замените его на адрес этого ПК в закрытой сети/VPN. В `ASR_API_KEY` укажите секрет своего ASR-сервиса. Не публикуйте Ollama напрямую в интернет. Подготовка GPU, загрузка весов и отдельный Compose описаны в [инструкции для ПК с моделями](deploy/gpu/README.md).

Для ASR непосредственно внутри worker вместо `self_hosted`:

```dotenv
ASR_PROVIDER=faster_whisper
INSTALL_LOCAL_AI=true
MODELS_PATH=./models
ASR_MODEL=/models/faster-whisper-large-v3
DIARIZATION_MODEL=/models/pyannote-speaker-diarization-community-1
ASR_DEVICE=cpu
ASR_COMPUTE_TYPE=int8
```

Предварительно скачайте модели в `MODELS_PATH` согласно инструкции. CPU-вариант может работать медленно; для NVIDIA GPU предусмотрен отдельный [GPU Compose](deploy/gpu/compose.yaml). LLM продолжает настраиваться отдельно через Ollama или API. Согласно [протоколу Windows GPU](deploy/gpu/windows/WINDOWS.md), Whisper large-v3 и Community-1 прошли техническую проверку на синтетическом аудио, в том числе без доступа к сети после загрузки весов. Это не подтверждает качество на реальных приёмах или доступность GPU-узла с удалённого backend.

Для Windows также подготовлен вариант **ASR + LM Studio** без Docker на компьютере с моделями: [установка, команды запуска и результаты испытаний](deploy/gpu/windows/WINDOWS.md). LM Studio подключается через `LLM_PROVIDER=openai_compatible`; доступны `LLM_RESPONSE_FORMAT`, `LLM_REASONING_EFFORT`, `LLM_MAX_TOKENS` и `LLM_TEMPERATURE`. Проверенные Gemma 3 4B и Qwen 3.5 9B выдавали ошибки извлечения фактов, поэтому этот путь остаётся экспериментальным. Подключение к удалённому backend требует отдельной проверки сети и ограничения доступа к API моделей.

После изменения адресов, моделей или ключей пересоздайте сервисы; при изменении `INSTALL_LOCAL_AI` пересоберите worker:

```powershell
docker compose up -d --build --force-recreate --no-deps api worker
```

### Демо и разработка

Для нового демонстрационного окружения выполните `./scripts/setup.ps1 -Demo` вместо обычного setup, запустите Compose и затем:

```powershell
docker compose exec api python -m app.seed_demo
```

Логин — `doctor@medhub.local`, пароль — `DEMO_PASSWORD` из вашего `.env`. Для уже существующего файла задайте `DEMO_MODE=true` и пароль от 12 символов, затем пересоздайте API/worker. Повторный seed не меняет пароль существующего кабинета.

Разработка интерфейса с работающим API:

```powershell
docker compose stop ui
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Проверки выполняются из соответствующих каталогов: `python -m pytest -q` в `backend`, `pnpm test` и `pnpm build` в `frontend`. Backend-зависимости: `pip install -r requirements.txt -c requirements.lock` в отдельном Python-окружении.

Публичное демо запускается также без Docker: Nginx отдаёт UI, systemd запускает `medhub-api` и `medhub-worker`. Скрипты [установки](deploy/install-service-release.sh) и [обновления](deploy/update-service-release.sh) используют `/opt/medhub/current` и отдельную конфигурацию `/opt/medhub/shared/app.env`. Docker Compose остаётся доступным вариантом упаковки: [production Compose](deploy/compose.production.yaml).

## Что готово

- Регистрация и вход по паролю, XML-подпись для входа и привязки ИИН; QR, NCALayer и ссылка eGov Mobile.
- Общий поиск пациентов, карточки с ИИН, маски ввода и определение даты рождения из ИИН с ручным уточнением. Телефон пациента и врача необязателен; введённый номер проверяется.
- Первичные и повторные приёмы, ссылки на предыдущие листы, таймер, пауза и раздел «Мои приёмы».
- Согласие пациента: PDF, QR через SIGEX, локальная проверка ЭЦП НУЦ, статусы проверки, история и отзыв; восстановление проверки при временных ошибках.
- Микрофон с сохранением выбора, запись фрагментами, загрузка аудиофайла, звуки начала/окончания/обрыва.
- Расшифровка с голосами и ролями, дополнение полей без удаления ручных данных, перегенерация с учётом правок.
- Поиск по справочнику МКБ-10, варианты диагноза и обследований для проверки врачом. Каталог содержит 14 586 кодов из среза 14.04.2021; применимость к конкретной клинике требует проверки. [Источник справочника](backend/app/catalogs/README.md).
- Черновики, проверка врачом, PDF с логотипом UMC, зашифрованный архив и история изменений.
- Получение утверждённых приёмов через API и пример исходящей интеграции с МИС.

### Известные ограничения

- ASR и LLM могут ошибаться в терминах, отрицаниях, ролях и клинических сведениях; результат требует проверки врачом. Метки голосов между фрагментами не гарантируют устойчивой идентификации человека.
- Новая запись и загрузка доступны только в первые 15 минут приёма и закрываются после его завершения. Сохранённое аудио можно прослушивать; лист — дорабатывать.
- Файлы — до 80 МБ; перед OpenAI аудио сжимается, лимит после сжатия — 24 МБ. Скорость зависит от длительности записи, очереди, сети и провайдера.
- Автоматическое маскирование неполное; исходное аудио в облачном режиме не обезличивается до первой отправки. Обезличенный текст также может содержать косвенные идентификаторы.
- Локальный ASR технически проверен на коротких синтетических записях. Качество казахской речи, шумных и длительных реальных приёмов не измерено; проверенные локальные LLM допускали ошибки извлечения фактов. Полный сценарий с удалённого backend и другие API-провайдеры требуют отдельной проверки.
- Создание QR SIGEX и программная обработка подписей проверены; завершённое подписание действующей ЭЦП владельцем после последнего исправления требует отдельной проверки. Чужой ИИН, неподтверждённая подпись или просто возврат из eGov не дают доступ.
- Демонстрационный API МИС не заменяет интеграционные испытания с конкретной медицинской системой. Для нескольких процессов API нужна межпроцессная координация фоновых задач подписания.

Команды воспроизводимых проверок приведены в разделе запуска; результаты отдельных этапов — в [протоколах приёмки](docs/acceptance-2026-09-30-smart-consult.md) и [проверке сервиса](docs/verification-2026-09-30.md). Эти протоколы относятся к указанным в них версиям и сценариям; обновление README не означает повторного прогона всего набора тестов. Автотесты не являются оценкой клинической точности или подтверждением всех внешних интеграций. Подробнее: [ЭЦП и согласие](docs/sigex-patient-consent.md), [потоковая запись](docs/live-recording.md), [журнал изменений](CHANGELOG.md).

### Проверка ЭЦП на сервере

SIGEX используется для QR и передачи подписей из eGov Mobile. Регистрация приватных документов и вызов SIGEX `/verify` не используются. Криптографию XML/CMS проверяет локальный модуль НУЦ с Java 17+, цепочкой доверия и OCSP. Установка SDK: [backend/verifier/README.md](backend/verifier/README.md). Для временной работы с ручным согласием врача задайте `CONSENT_SIGNATURE_REQUIRED=false`; по умолчанию требование ЭЦП включено.
